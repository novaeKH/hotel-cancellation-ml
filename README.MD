# Hotel Booking Cancellation

Модель для оценки риска отмены гостиничного бронирования в момент его создания.

Этот проект начинался как обычная задача бинарной классификации, но самое интересное появилось после первой версии модели. На старых данных она работала хорошо, а на новых качество заметно снизилось. Поэтому проект вырос из одного ML-notebook в небольшой полный цикл: исследование данных, обучение, анализ деградации, retraining, API и monitoring.

## Задача

Отель хочет заранее находить бронирования с высоким риском отмены и передавать их менеджерам для дополнительного подтверждения.

Здесь важно не просто найти как можно больше отмен. Если модель будет часто ошибаться, менеджеры получат слишком большой список обычных броней и перестанут ему доверять. Поэтому я выбрал понятное бизнес-условие: `Precision >= 0.70`, а среди подходящих порогов старался получить максимальный Recall.

Данные содержат 119 390 бронирований двух отелей. Отмены составляют около 37% выборки.

## С какими проблемами я столкнулся

### 1. Часть признаков нельзя использовать в момент прогноза

В исходном датасете есть колонки, которые выглядят очень полезными для модели, но появляются уже после создания брони. Например, итоговый статус или изменения бронирования. Если оставить их, модель покажет красивое, но бесполезное качество.

Я зафиксировал момент прогноза — сразу после создания брони — и убрал `reservation_status`, `reservation_status_date`, `booking_changes`, `assigned_room_type` и `days_in_waiting_list`.

### 2. Случайный split не подходит для этой задачи

Поведение клиентов и структура бронирований меняются со временем. При случайном разделении в train и validation перемешались бы старые и новые периоды, поэтому оценка получилась бы слишком оптимистичной.

Готовой даты создания брони в данных нет, поэтому я восстановил её как дату заезда минус `lead_time`. После этого все выборки идут строго из прошлого в будущее.

### 3. Хорошей метрики на одной validation оказалось недостаточно

Первой рабочей моделью стала LightGBM. На старой validation она выполняла условие по Precision и находила большую часть отмен.

На следующем batch за февраль–апрель Precision снизилась примерно с `0.70` до `0.61`. Порог уже был выбран, поэтому я не стал подгонять его под новые данные, а сначала разобрался в причине ухудшения.

Оказалось, что изменились сразу две вещи:

- распределения признаков: например, медианный `lead_time` снизился с 77 до 47 дней, а `Non Refund` стал встречаться намного реже;
- связь некоторых признаков с target: большой `lead_time` стал хуже отделять отмены, а история предыдущих отмен перестала работать так же, как на train.

Feature importance и SHAP показали, что LightGBM как раз сильно опиралась на эти признаки. Я рассматриваю это как возможное изменение концепции, но не называю доказанным concept drift по одному batch.

### 4. Обычное переобучение могло сохранить влияние старых данных

После появления новых labels возникла гипотеза: старой истории намного больше, поэтому при retraining она может продолжать задавать модели прежние закономерности.

Чтобы проверить это, я обучил одну и ту же CatBoost четырьмя способами:

- только на старых данных;
- на всей доступной истории;
- на последних 12 месяцах;
- на всей истории с повышенным весом свежих наблюдений.

Для recency weighting использовал простую схему: через заданное число месяцев вес наблюдения уменьшается вдвое. Проверил half-life 6, 12 и 18 месяцев. Силу weighting и размер окна выбирал только по апрелю, не используя май–август для настройки.

| Стратегия | PR-AUC, апрель | PR-AUC, май–август |
|---|---:|---:|
| Только старые данные | 0.726 | 0.654 |
| Вся история | 0.743 | **0.685** |
| Recency weighting | **0.748** | 0.680 |
| Последние 12 месяцев | 0.740 | 0.672 |

Recency weighting немного выиграл на апреле, но на следующем периоде преимущество исчезло. Поэтому я не стал усложнять обучение и оставил обычный retraining на всей истории. Изначальная гипотеза о слишком сильном влиянии старых данных в этом эксперименте не подтвердилась.

## Что получилось в итоге

На одном и том же monitoring-периоде CatBoost v2 дала более точный список рискованных броней, чем LightGBM v1:

| Модель | Precision | Recall | PR-AUC |
|---|---:|---:|---:|
| LightGBM v1 | 0.575 | **0.765** | 0.661 |
| CatBoost v2 | **0.661** | 0.540 | **0.685** |

CatBoost стала лучше по Precision и PR-AUC, поэтому её можно использовать как новую версию. Recall при этом снизился — это осознанный trade-off, потому что для менеджеров важнее качество списка срабатываний.

Бизнес-цель `Precision >= 0.70` на май–август всё равно не достигнута. Я не скрываю это новым подбором порога: для следующего решения нужны более свежие данные. Полностью независимого периода после августа в датасете уже нет.

В результате в проекте есть не только обученная модель, но и понятный сценарий её дальнейшей жизни:

```text
новые данные → monitoring → разбор деградации → retraining candidate
             → сравнение с текущей моделью → замена только при улучшении
```

Сам по себе drift ничего автоматически не запускает. Сначала должно подтвердиться падение качества, а новая модель должна показать реальное улучшение.

## Как запустить

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
jupyter lab
```

Локальный запуск API:

```bash
uvicorn api.main:app --reload
```

Запуск в Docker:

```bash
docker build -t hotel-cancellation .
docker run --rm -p 8000:8000 hotel-cancellation
```

После запуска Swagger доступен по адресу `http://127.0.0.1:8000/docs`, а информация о загруженной модели — по адресу `http://127.0.0.1:8000/health`.
