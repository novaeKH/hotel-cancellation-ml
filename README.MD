# Hotel Booking: поздние отмены и сезонность

Анализ бронирований двух отелей и прогноз поздней отмены или незаезда.
Момент прогноза — вечер перед датой заезда, когда бронь ещё активна.
Сравниваю простой сезонный ориентир, Logistic Regression и CatBoost,
затем проверяю ежемесячное переобучение и пользу календарных признаков.

## Результаты

Проверка по месяцам с марта по август 2017: **19 058 броней**, из них
**357 поздних отмен и незаездов** — 1.87%.
Для каждого отеля и дня заезда выделяю верхние 10% броней по риску.
Из-за округления вверх в список попали 2 069 броней, или 10.86% выборки.

| Модель | Average Precision | ROC-AUC | Precision списка | Recall списка |
|---|---:|---:|---:|---:|
| Частота по отелю и месяцу | 0.0208 | 0.5244 | 1.45% | 8.40% |
| Logistic Regression | 0.0328 | 0.6297 | 4.06% | 23.53% |
| CatBoost, обучение перед мартом | 0.0431 | 0.6344 | 3.67% | 21.29% |
| CatBoost, ежемесячное обучение | 0.0436 | 0.6350 | 4.06% | 23.53% |
| CatBoost, ежемесячно без календаря | 0.0454 | 0.6437 | 4.01% | 23.25% |

CatBoost с ежемесячным обновлением нашёл **84 из 357** поздних отмен.
Доля отмен в его списке в 2.17 раза выше общей доли в выборке.
Logistic Regression нашла столько же отмен при этом размере списка, хотя
её AP ниже. При precision около 4% большинство проверяемых броней всё равно
заканчивается заездом, поэтому практическая польза зависит от стоимости проверки.

Переобучение немного улучшило результат фиксированной модели. Календарные
признаки явного выигрыша не дали: вариант без них оказался немного лучше по AP.
Основной результат привожу для модели с календарём, выбранной на validation.

## Данные и момент прогноза

Источник — [Hotel Booking Demand](https://www.kaggle.com/datasets/jessemostipak/hotel-booking-demand),
119 390 бронирований City Hotel и Resort Hotel с заездами с июля 2015 по
август 2017. В [статье авторов](https://doi.org/10.1016/j.dib.2018.11.126)
описана выгрузка признаков накануне заезда. Поэтому прогноз при создании
брони здесь заменён прогнозом позднего исхода.

В модельную выборку входят брони с `lead_time >= 1`, которые не были отменены
до дня заезда. Отмена в день заезда или позднее, включая незаезд, считается
положительным исходом. Таких активных броней во всём наборе 70 908.
Время статуса доступно с точностью до дня.

В EDA рассматриваю пропуски, нулевое число гостей и 31 994 полностью совпадающие
строки. Совпадения оставлены: идентификаторов исходных броней нет, и одинаковые
записи могут относиться к групповому бронированию. Объём на графиках — число
броней в выгрузке, а не загрузка номерного фонда.

## Признаки и проверка по времени

Использую отель, срок ожидания, состав гостей, длительность проживания, канал
бронирования, сегмент, тип номера, агентство, компанию и календарь заезда.
Добавляю число гостей и ночей, наличие агентства и компании. Всего 23 признака.

Статус и его дата нужны только для целевой переменной и доступности исхода.
Исключены ADR и тип депозита, связанные с транзакциями, а также страна,
назначенный номер, изменения брони и другие поля с неясным временем обновления.
Обработка признаков общая для обучения и API.

- **Validation:** январь–февраль 2017. Сравниваются глубина CatBoost 4 и 6,
  вся доступная история и последние 12 месяцев. Выбраны depth=6 и 12 месяцев
  по общей AP двух месяцев; 400 деревьев, learning rate=0.05.
- **Test:** март–август 2017. Параметры остаются фиксированными. Перед каждым
  месяцем обучение использует только предыдущие заезды, чей итоговый статус
  уже известен к этой дате.
- **Список проверок:** 10% отдельно для каждого отеля и даты заезда,
  округление вверх. Равные оценки упорядочиваются случайно с seed=42.

В EDA отдельно показан край выгрузки: у недавно созданных броней длинный
`lead_time` переносит заезд за пределы набора. Поэтому разбиение строится
по датам заезда. Два отеля и чуть больше двух лет наблюдений позволяют
сравнить подходы на этих данных; для проверки устойчивости нужны новые месяцы.

## Воспроизведение

Использован Python 3.11. Скачать `hotel_bookings.csv` с Kaggle и положить
в `data/raw/`. Исходные данные и веса модели исключены из Git.

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
export PYTHONPATH=src
export OPENBLAS_NUM_THREADS=2
export OMP_NUM_THREADS=2
python -m hotel_booking.experiment
```

Другой путь к CSV можно передать через `--data-path`. Полный запуск сохраняет
отчёты в `reports/evaluation/`, предсказания и последнюю модель — локально.
Версии библиотек, seed и SHA-256 исходного файла записаны в `run.json`.
Ноутбуки строят таблицы и графики из сохранённых отчётов; их можно выполнить
без повторного обучения в Jupyter или VS Code.

## Демонстрация

После обучения:

```bash
pip install -r requirements-api.txt
PYTHONPATH=src uvicorn api.main:app --port 8000
```

Открыть `http://localhost:8000/docs`. Метод `/predict` принимает параметры
активной брони накануне заезда и возвращает вероятность поздней отмены и дату
границы обучения. Для выбора списка проверок нужно ранжировать все брони
отеля на одну дату; отдельное предсказание не задаёт размер такого списка.

В репозитории также есть Dockerfile. Образ собирается после обучения, когда
появилась папка `models/trained/`.
